**여기서 에셋이나 코드를 꺼내 쓰지 않는다.** 게임 규칙과 연출 방식은 배울 수 있지만

## 1. 결론 — 부러운 건 움직임이 아니다

> **카이로소프트 캐릭터가 살아 보이는 이유는 이동 로직이 좋아서가 아니다.
> 오히려 그쪽 이동은 우리보다 훨씬 단순하다.**

카이로소프트 계열 연출의 실제 특징은 이렇다.

| 항목 | 카이로소프트 | 우리 현황 |
| --- | --- | --- |
| 걷기 프레임 수 | **2~4프레임** | 8방향 × 6프레임 = 48프레임 |
| 가감속 | **없음.** 등속 | 있음 (locomotion transitions) |
| 캐릭터끼리 충돌 | **거의 없음.** 겹쳐도 그냥 지나간다 | 반경 충돌 + 양보 + 재계획 |
| 경로탐색 | 단순. 직선에 가깝다 | 하위칸 정밀 충돌 |
| **말풍선·이모트** | **항상 뜬다** | **없음** |
| **떠오르는 숫자** | **항상 뜬다** | **없음** |
| **사건 반응 동작** | 점프·땀·반짝임 | 없음 |

**이동 품질은 우리가 이미 이긴다.** 우리에게 없는 건 **피드백 밀도**다.

캐릭터가 아무 말도 안 하고, 아무 숫자도 안 띄우고, 아무 반응도 안 하면
아무리 부드럽게 걸어도 인형이 미끄러지는 것으로 보인다.
반대로 2프레임짜리 도트가 등속으로 걸어도 머리 위에 `…`와 `+15`가 계속 뜨면 살아 있어 보인다.

**이게 이번에 가져올 것이다.**

## 3. 가져올 규칙 네 가지

### 3-1. 이모트 말풍선 — 글자가 아니라 그림 ★최우선

카이로소프트는 머리 위에 **글자를 거의 안 쓴다.** 아이콘 하나를 띄운다.
글자는 언어에 묶이고 작으면 안 읽히지만, 아이콘은 멀리서도 즉시 읽힌다.

2000년 사무실에 맞춘 최소 세트다.

| 이모트 | 언제 |
| --- | --- |
| `…` | 이동 중, 생각 중 |
| `!` | 계약 도착, 사건 발생 |
| 💡 | 아이디어. 기획 단계 진입 |
| 💧(땀) | 체력 낮음, 마감 임박 |
| 😤 | 스트레스 높음 |
| ⚙ | 제작 단계 작업 중 |
| 🎨 | 디자인 단계 작업 중 |
| ☕ | 휴식 |
| ✓ | 단계 완료 |
| ★ | 품질 좋게 완료 |
| ✉ | 전화·팩스 수신 |
| 💤 | 대기, 할 일 없음 |

**12개면 충분하다.** 아이콘 하나 크기는 캐릭터 머리의 절반쯤.

규칙:

- 한 캐릭터에 **한 번에 하나만** 띄운다. 겹치면 즉시 지저분해진다
- **1.5~2.5초 표시 후 사라진다.** 상시 표시는 배경이 되어 눈에 안 들어온다
- 뜰 때 아래에서 위로 살짝 튀어오르고(0.15초), 사라질 때 페이드
- 우선순위를 둔다. 땀·스트레스 > 완료 > 단계 > 이동
- **말풍선은 캐릭터를 따라가되 화면 밖으로 안 나간다** (화면 경계에서 안쪽으로 붙는다)

### 3-2. 떠오르는 숫자 — 결과가 눈에 보여야 한다

카이로소프트의 핵심이다. 작업이 진행되면 캐릭터에서 숫자가 튀어나온다.

우리에게 맞춘 목록이다.

| 표시 | 색 | 언제 |
| --- | --- | --- |
| `+3 인시` | 흰색 | 계약 작업 1회 반영 |
| `+15만원` | 금색 | 계약 완료 대금 |
| `-8만원` | 붉은색 | 착수비, 비용 지출 |
| `+2 평판` | 민트 | 계약 완료 |
| `-2 평판` | 붉은색 | 마감 실패 |
| `체력 -5` | 회색 | 과로 |
| `유대 +1` | 분홍 | 회복 활동 |

규칙:

- **캐릭터 머리 위에서 생겨 위로 40~60px 올라가며 페이드**, 0.8~1.2초
- 같은 캐릭터에서 연속 발생하면 **살짝 옆으로 밀어** 겹치지 않게 한다
- 큰 값은 글자를 키운다. `+150만원`은 `+3만원`보다 커야 한다
- **배속에 비례해 빨라진다.** 4배속에서 1.2초짜리가 그대로면 화면이 숫자로 덮인다

이게 들어가면 **"뭔가 진행되고 있다"가 처음으로 눈에 보인다.**
지금은 관리 화면을 열어야만 진행을 알 수 있다.

### 3-3. 사건 반응 동작 — 짧고 과장되게

카이로소프트는 프레임이 적은데도 살아 보인다. **반응이 과장돼 있기 때문이다.**

| 동작 | 구현 | 언제 |
| --- | --- | --- |
| 점프 | Y로 0.2 units 튀었다 내려옴, 0.25초 | 계약 완료, 좋은 사건 |
| 흠칫 | 뒤로 0.1 units 밀렸다 복귀, 0.15초 | 나쁜 사건, 실패 |
| 흔들림 | 좌우 0.05 units 3회, 0.3초 | 스트레스 폭발, 쓰러짐 직전 |
| 고개 끄덕 | 스프라이트 Y 스케일 0.95↔1.0, 0.2초 | 대화, 지시 수락 |

**전부 Transform 한 줄로 된다. 새 아트가 필요 없다.**
이게 48프레임 이동 애니메이션보다 "살아 있음"에 기여가 크다.

### 3-4. 정지 중 미세 동작 — 멈추면 죽어 보인다

사람이 완전히 정지하면 즉시 인형이 된다. 카이로소프트는 서 있어도 항상 조금 움직인다.

- **호흡 흔들림**: 스프라이트를 2초 주기로 Y 스케일 1.0↔1.02. 상시
- **2~5초마다 작은 동작 하나**: 주변 보기(방향 전환 후 복귀), 서류 넘기기, 시계 보기
- **결정론 유지**: 주기와 선택은 `StableRandom(agentId, elapsedMinute)`으로 뽑는다.
  프로젝트 규칙이 `UnityEngine.Random` 금지다

현재 3D 캐릭터의 idle/micro-action 검수는 `FAMILY_3D_CHARACTER_HANDOFF_2026-08-24.md`의 실제 게임
재검수 뒤 별도 단계에서 다룬다.

## 4. 왜 이게 코덱스와 겹치지 않나

전부 **표시 계층**이다. 이동·충돌·경로에 손대지 않는다.

| 계층 | 담당 |
| --- | --- |
| 격자·가구·충돌·경로·착석 | **코덱스** (현재 작업 중) |
| 캐릭터 위치·방향 | **코덱스** |
| **위치를 읽어서 그 위에 아이콘·숫자·미세동작을 얹는 것** | **여기** |

새로 만드는 파일은 이렇게 격리된다.

```
Presentation.Unity/Feedback/OfficeEmoteBubble.cs        아이콘 말풍선
Presentation.Unity/Feedback/OfficeFloatingNumber.cs     떠오르는 숫자
Presentation.Unity/Feedback/OfficeReactionMotion.cs     점프·흠칫·흔들림
Presentation.Unity/Feedback/OfficeIdleBreath.cs         호흡·미세동작
Presentation.Unity/Feedback/OfficeFeedbackDirector.cs   무엇을 언제 띄울지 결정
Simulation/Feedback/OfficeFeedbackSignal.cs             순수 신호 정의 (읽기 전용)
```

**기존 파일 중 수정이 필요한 것은 없다.**
`OfficeFeedbackDirector`가 `OfficeWorkerAgent`의 위치와 `GameState`의 사건을 **읽기만** 한다.

접점이 하나 있다. **어떤 사건이 일어났는지 알아야 한다.**
지금은 계약 완료·실패가 `PrototypeBootstrap`의 `_notice` 문자열로만 표현된다.
그래서 순수 계층에 신호 목록을 하나 두면 배선이 깔끔해진다.

```csharp
// 예시. 값만 담는 읽기 전용 신호. 화면이 이것을 소비한다.
OfficeFeedbackSignal { memberId, kind, amount, atMinute }
// kind: ContractProgress, ContractPaid, CostPaid, ReputationUp, ReputationDown,
//       StaminaDrop, StressSpike, BondUp, StageEnter, StageDone
```

**이 신호 정의만 합의하면 나머지는 서로 독립적으로 만들 수 있다.**

## 6. 카이로소프트에서 배울 것 하나 더 — 화면 밀도

이건 규칙이 아니라 태도다.

- **사무실 전체가 한 화면에 들어온다.** 스크롤이 없다. 전부 한눈에 보인다
- **한 책상에 한 명.** 누가 어디서 뭘 하는지 세지 않아도 안다
- **정보는 캐릭터 위에 있다.** 별도 패널을 열지 않아도 진행이 보인다

우리 13×13 타일 사무실이 이미 한 화면에 들어오므로 첫 줄은 만족한다.
세 번째 줄이 지금 없는 것이고, 3-1·3-2가 그것을 해결한다.

## 7. 권장 순서

| 순위 | 항목 | 크기 | 효과 |
| --- | --- | ---: | --- |
| 1 | **떠오르는 숫자** (3-2) | 소 | 아트 0장. 진행이 처음으로 눈에 보인다 |
| 2 | **정지 중 호흡·미세동작** (3-4) | 소 | 아트 0장. 멈춰 있어도 살아 보인다 |
| 3 | **반응 동작 4종** (3-3) | 소 | 아트 0장. 사건이 몸으로 표현된다 |
| 4 | **이모트 말풍선** (3-1) | 중 | 아이콘 13장 필요. 체감이 가장 크다 |
| 5 | 신호 정의 합의 (4장) | 소 | 1~4를 깔끔하게 배선하기 위한 전제 |

**1~3번은 새 아트가 하나도 필요 없다.** 오늘 시작할 수 있다.
5번을 먼저 합의하면 1~4를 순서 상관없이 붙일 수 있다.

## 8. 성공 판정

1. **관리 화면을 열지 않고도** 회사가 일하고 있는 게 보이는가?
2. 캐릭터가 멈춰 있을 때도 살아 있어 보이는가?
3. 계약이 완료된 순간을 **화면만 보고** 알 수 있는가?
4. 누가 지쳤는지 숫자를 안 보고 알 수 있는가?
5. 4배속에서도 화면이 숫자로 뒤덮이지 않는가?

지금은 1~4가 전부 "아니오"다. 5번은 배속 비례 처리를 안 하면 새로 생길 문제다.
