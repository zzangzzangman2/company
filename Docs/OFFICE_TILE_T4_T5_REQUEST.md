## 2. 먼저 막고 가야 할 것 — 가구 아트가 잘려 있다 ★차단 요인

**T4를 시작하기 전에 이것부터 확인해야 한다.** 안 그러면 어떤 배치를 해도 화면이 틀린다.

### 측정 결과

`Assets/Art/Office/Pixel/Modules/`의 12종 중 **8종이 프레임 가장자리에서 잘렸거나 옆 칸 픽셀을 물고 있다.**

| 항목 | 프레임 | 피사체 bbox | 문제 |
| --- | --- | --- | --- |
| `swivel_chair` | 512×341 | (0, 37, **512**, 305) | **좌우 양쪽 끝까지 닿음.** 회전의자가 프레임 폭 전체를 채울 리 없다 |
| `reception_counter` | 512×341 | (0, 64, **512**, 332) | 좌우 양쪽 |
| `workstation` | 512×341 | (49, 34, **512**, 334) | 오른쪽 잘림 |
| 그 외 5종 | 512×341 | — | 한 변 이상 접촉 |

의자와 접수 카운터의 bbox가 **512×268로 완전히 동일**하다. 서로 다른 물건인데 같은 크기가 나올 수 없다.

### 원인

아틀라스 원본은 **1536×1024**다. 파일명이 `4x3`이므로 칸은 **1536÷4 = 384** 폭이어야 한다.
그런데 추출된 모듈은 **512** 폭이다. 384가 아니라 512로 잘랐다.

- 512 폭으로 자르면 3열밖에 안 나오는데 모듈은 12개다
- 384 폭으로 잘라 보면 **윗줄 4칸이 모두 칸 경계를 넘는다** (아래 두 줄은 여백이 정상)

즉 **원본 아틀라스 자체가 칸 경계를 지키지 않고 그려졌고**, 추출 폭도 어긋나 있다.
결과적으로 각 모듈 PNG는 자기 물건이 잘려 있거나 옆 물건 조각을 포함한다.

### 요청

셋 중 하나를 골라 **T4 전에** 해결한다.

| 방안 | 내용 | 권장 |
| --- | --- | --- |
| **A** | 가구 12종을 **1장에 1개씩** 투명 배경으로 다시 생성 | **권장.** ImageGen 파이프라인이 이미 있고 칸 경계 문제가 원천 제거된다 |
| B | 아틀라스를 균등 격자가 아니라 **물건별 bbox로** 잘라낸다 | 원본이 겹쳐 그려졌으면 여전히 옆 조각이 섞인다 |
| C | 그대로 쓴다 | 안 된다. 배치할수록 겹침이 눈에 띈다 |

첨부한 contact sheet에서 빨간 테두리가 잘린 항목이다.

## 3. T4 — 가구 배치와 충돌

### 3-1. 책상·의자·컴퓨터 구성 — 확정

사용자 결정: **컴퓨터는 책상과 세트로 둔다. 대신 거기에 실제로 앉아야 한다.**

| 물건 | `kindId` | 아트 | footprint | `blocksMovement` |
| --- | --- | --- | --- | --- |
| 책상 + 컴퓨터 | `desk_with_pc` | `office_workstation` | **2 × 1** | **true** |
| 의자 | `swivel_chair` | `office_swivel_chair` | **1 × 1** | **false** |

컴퓨터 단독 오브젝트는 만들지 않는다. `office_desktop_pc` 아트도 필요 없다.
`kindId`를 `desk_with_pc`로 두는 것은 나중에 분리하고 싶어질 때를 위한 이름일 뿐,
이번에 분리 작업을 하지 않는다.

**핵심은 "세트로 두되 앉을 수 있어야 한다"이다.** 그래서 아래 3-2와 4-1이 이번 작업의 중심이다.

### 3-2. 의자는 막으면 안 된다 ★가장 중요

```csharp
new PlacedOfficeFurniture("desk_a", "desk_with_pc", new(4,4), 2, 1, SouthEast, blocksMovement: true)
new PlacedOfficeFurniture("chair_a", "swivel_chair", new(4,5), 1, 1, NorthWest, blocksMovement: false)
                                                                              // ^^^^^^^^^^^^^^^^^^
```

**의자 칸은 walkable로 남겨야 한다.** 캐릭터가 그 칸으로 걸어 들어가서 앉기 때문이다.
`OfficeGrid` 생성자는 `blocksMovement = true`인 가구가 walkable 칸에 있으면 예외를 던지므로,
의자를 `true`로 두면 **레이아웃 생성 자체가 실패**하거나, walkable을 꺼서 **앉을 수 없게** 된다.

### 3-3. 바닥 점유와 화면 높이를 구분한다

측정값이다. 타일 1칸 = **1.778 × 0.889** world units (320×160 px, PPU 180).

| 가구 | 피사체 크기 | 타일 환산 (가로 × 세로) |
| --- | --- | --- |
| workstation | 2.57 × 1.67 u | 1.4 × 1.9 |
| swivel_chair | 2.84 × 1.49 u | 1.6 × 1.7 |
| meeting_table | 2.57 × 1.61 u | 1.4 × 1.8 |
| filing_cabinet | 1.28 × 1.73 u | 0.7 × 2.0 |
| potted_plant | 1.58 × 1.66 u | 0.9 × 1.9 |

세로가 전부 1.7~2.1타일로 나오는데, **이건 바닥 점유가 아니라 화면상 높이다.**
등각에서 물건은 바닥 마름모 위로 솟아오르기 때문이다.

- **바닥 점유(footprint)** = 충돌·배치 판정용. 대부분 **1×1**, 책상·회의탁자는 **2×1**
- **화면 높이** = 렌더용. 스프라이트가 알아서 위로 뻗는다

**pivot을 반드시 바닥 마름모 중심에 둔다.** 스프라이트 중앙이 아니다.
pivot이 틀리면 가구가 공중에 뜨거나 바닥에 파묻힌다.

### 3-4. 정렬

가구와 캐릭터를 **같은 SpriteRenderer 정렬 그룹**에 넣고 `x + y`로 함께 정렬한다.
가구 레이어와 캐릭터 레이어를 나누면 "항상 앞" 또는 "항상 뒤"가 되어 입체감이 죽는다.

T3에서 이미 `sorting=x+y`가 통과했으므로 같은 규칙을 가구로 확장하면 된다.

## 4. T5(일부) — 앉아서 일하기

이번 범위는 **좌석에 앉는 것까지**다. 계약 인시 연동은 다음이다.

### 4-1. 좌석 배치 불변식 ★"실제로 앉는다"의 핵심

좌표 규약(어느 방향이 북서인지)은 이미 코드에 정해져 있으므로 여기서 다시 정하지 않는다.
대신 **규약과 무관하게 성립해야 하는 불변식**을 정의한다. QA는 이걸 검사한다.

| # | 불변식 |
| --- | --- |
| 1 | 좌석 칸은 그 좌석이 속한 책상 footprint에 **4방향으로 인접**해야 한다 (대각선 금지) |
| 2 | 좌석 칸은 **`IsWalkable == true`** 여야 한다 |
| 3 | `seat.Facing`은 **좌석 칸에서 책상 칸을 향하는 방향**과 일치해야 한다 |
| 4 | 의자 가구의 `Origin`은 **좌석 칸과 같은 칸**이어야 한다 |
| 5 | 한 책상에 좌석은 **1개 이상**, 좌석마다 의자 가구가 **정확히 1개** 대응 |

3번이 특히 중요하다. 이게 어긋나면 캐릭터가 **책상에 등을 돌리고 앉는다.**
사람이 눈으로 보기 전에 검사로 잡아야 한다.

### 4-2. 의자와 캐릭터의 앞뒤

앉으면 캐릭터와 의자가 **같은 칸**에 있으므로 `x + y` 정렬만으로는 앞뒤가 정해지지 않는다.
방향에 따라 규칙이 갈린다.

| 캐릭터가 보는 방향 | 의자 등받이 |
| --- | --- |
| 화면 위쪽(카메라 반대) — 등을 보임 | 캐릭터보다 **앞** (등받이가 등을 가림) |
| 화면 아래쪽(카메라 쪽) — 얼굴을 보임 | 캐릭터보다 **뒤** |

기존 페인팅 사무실이 같은 문제를 `OfficeSeatForegroundOcclusionMode`로 이미 다뤘다
(`DirectionalSpriteAnimator.cs:356~368`). **그 개념을 격자로 이관하면 된다. 새로 설계하지 않는다.**

### 4-3. 흐름

```
1. 목표 좌석 선택
2. 좌석 칸까지 경로 이동 (막힌 칸 통과 금지)
3. 좌석 칸 도착
4. 앉기 — 위치를 좌석 앵커로 스냅, 방향을 seat.Facing으로 고정
5. 의자 등받이 앞뒤를 4-2 규칙으로 결정
6. 작업 애니메이션 재생
7. 일어설 때 인접 walkable 칸으로 나온다
```

### 정확히 앉았는지의 정의

"정확히"를 눈대중이 아니라 수치로 정한다.

| 항목 | 기준 |
| --- | --- |
| 발 위치 | 좌석 칸 중심에서 **0.05 world units 이내** |
| 방향 | `seat.Facing`과 **정확히 일치** |
| 정렬 | 책상보다 **앞**(의자가 책상 남쪽이면), 뒤면 가려짐 |
| 겹침 | 캐릭터 bbox와 책상 bbox가 겹치되 **정렬 순서가 올바를 것** |

기존 `OfficeSeatPrecisionMotion.cs`가 페인팅 사무실에서 같은 문제를 이미 풀었다.
**그 접근을 격자 좌표로 이관하면 된다.** 새로 만들 필요 없다.

### 이번에 하지 않는 것

- 계약 인시 반영
- 자율 행동(학교·퇴실·복귀) 연동
- 좌석 배치 편집 UI
- A\* 경로탐색 (지금은 직선/수동 경로로 충분하다)

## 7. 배치 예시 — 책상 4자리

좌표 규약은 코드에 이미 있으므로 아래는 **관계**만 보여 주는 예시다.
실제 좌표는 4-1의 불변식을 만족하도록 정하면 된다.

```csharp
// 책상 하나 + 그 앞 의자 하나가 한 세트다.
// 의자는 반드시 blocksMovement: false — 캐릭터가 그 칸에 들어가야 앉는다.

new PlacedOfficeFurniture("desk_a",  "desk_with_pc",  deskACell,  2, 1, facingDesk,  blocksMovement: true);
new PlacedOfficeFurniture("chair_a", "swivel_chair",  seatACell,  1, 1, facingSeat,  blocksMovement: false);
new OfficeSeatSlot("seat_a", "chair_a", seatACell, facingSeat);
//                            ^^^^^^^^ 좌석은 의자 가구에 붙는다. 책상이 아니다.
//   facingSeat = seatACell 에서 deskACell 을 향하는 방향 (불변식 3)
```

이 세트를 4개 만들면 가족 4명이 각자 자리에 앉는다.
나머지 가구(캐비닛·화분·정수기 등)는 `blocksMovement: true`로 벽 쪽에 배치해
**"부딪히는지" 검사(3번)의 표본**으로 쓴다.

### 좌석 수

가족이 4명이므로 **책상 4개 + 의자 4개**가 최소다.
직원 고용은 이번 범위가 아니므로 지금은 4자리면 충분하다.
