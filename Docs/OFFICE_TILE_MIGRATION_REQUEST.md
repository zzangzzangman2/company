## 0. 결론

> **타일 기반으로 가는 게 맞다. 다만 이유는 메모리가 아니다.**

메모리는 이 게임에서 문제가 아니다. 1920×1080 두 장은 부담이 아니다.
진짜 이유는 이것이다.

> **지금 구조로는 사무실이 넓어질 수 없다.**

`Docs/ULTIMATE_VISION.md`와 `COMPANY_SYSTEM.md`가 이미 성장 사다리를 못박아 뒀다.

```
집 작업공간 → 작은 사무실 → 직원 5명 사무실 → 부서 분리 사무실 → 본사 → 공장·연구소
```

그런데 지금 사무실은 **그림 한 장**이다. 단계마다 새 그림을 그려야 하고,
그릴 때마다 책상 좌표를 손으로 다시 재야 한다. 그건 6단계 × 매번 재측정이다.
**성장이 게임의 핵심인데 성장할 수 없는 구조를 쓰고 있다.**

그리고 앞 문서에서 잡은 버그들(캐릭터 3배 축소, 책상 위치 어긋남)도
이 구조에서 파생된 것이라 하나씩 고쳐도 계속 재발한다.

## 1. 지금 왜 무너지는가 — 좌표계가 셋이다

`PrototypeProjectBuilder.cs`를 따라가면 사무실이 이렇게 만들어진다.

```
CreateOffice()                      →  3D 프리미티브 사무실 + 웨이포인트   (좌표계 ①)
  ↓
OfficeVisualV2Presenter.Configure() →  1920×1080 페인팅을 카메라에 맞춰 늘림 (좌표계 ②)
  ↓
OfficeVisualV2Calibration           →  아트 픽셀 ↔ 월드를 호모그래피로 억지 연결 (좌표계 ③)
```

세 좌표계가 **손으로 맞춘 상수로만** 이어져 있다.

```csharp
// OfficeVisualV2Calibration.cs — 전부 손으로 잰 값
DeskAWorldCenter = (11.4f, 4.4f);      DeskAArtCenter = (813.5f, 376.5f);
DeskAApproachArt = (814f, 500f);       DeskASitArt    = (814f, 416f);
DeskAMonitorArt  = (816f, 223f);       PrinterArt     = (600f, 400f);
```

책상 하나를 옮기면 이 숫자를 **전부 다시 재야 한다.**
그래서 지금 화면이 어긋나는 것이고, 그래서 플레이어가 가구를 옮기게 만들 수 없다.

**타일 격자는 이 셋을 하나로 합친다.** 좌표가 `(3, 5)` 같은 정수 두 개가 된다.

## 2. 제안 검토 — 맞는 것과 보정할 것

### 2-1. 타일 기반 시스템 ✅ 맞다, 이유만 보정

| 사장님 제안 | 판정 |
| --- | --- |
| 바닥을 타일로 쪼갠다 | **맞다** |
| 타일 몇 개를 반복 배치한다 | **맞다** |
| 2차원 배열로 통행 가능 여부를 판별한다 | **맞다. 그리고 이게 제일 중요하다** |
| 이유가 메모리다 | **아니다.** 진짜 이유는 레이아웃 변경과 경로탐색이다 |

마지막 항목이 핵심이다. `Docs/ARCHITECTURE.md`에 이미 이렇게 적혀 있다.

> 현재 경로는 사전 정의된 안전 통로다. **사무실 배치를 플레이어가 자유 편집하게 되면 경로 탐색 계층을 추가한다.**

**2차원 배열이 곧 경로탐색 그래프다.** 격자를 깔면 A\*가 그 위에 바로 올라간다.
지금처럼 통로를 손으로 정의할 필요가 없어진다.

### 2-2. 등각 투영 ✅ 맞다, 방법만 보정

> "정사각형 타일을 마름모꼴(2:1)로 눕혀서 배치합니다"

개념은 맞다. 다만 **실제 작업에서는 타일을 회전시키지 않는다.**
처음부터 **2:1 마름모 모양으로 그린 스프라이트**를 만들어서 넣는다.
정사각형 그림을 45도 돌리면 픽셀이 계단처럼 깨진다.

Unity에는 **Isometric Tilemap**이 내장돼 있다.
`Grid` 컴포넌트의 Cell Layout을 `Isometric` 또는 `Isometric Z as Y`로 두면
마름모 배치와 정렬을 엔진이 처리한다. 직접 구현할 필요가 없다.

### 2-3. 레이어 구조 ✅ 맞다, 한 층 더 필요

사장님 제안: 바닥 / 오브젝트 / 동적

실제로는 네 층이 필요하다.

| 층 | 내용 | 정렬 |
| --- | --- | --- |
| 바닥 | 장판, 카펫, 타일 | 항상 최하단 |
| 오브젝트 | 책상, 파티션, 캐비닛 | **(x+y) 기준 동적 정렬** |
| 동적 | 캐릭터 | **(x+y) 기준 동적 정렬** — 오브젝트와 **같은 층에서 섞여야 한다** |
| 상단 고정 | 벽 위쪽, 천장 조명, 창문 | 항상 최상단 |

**오브젝트와 캐릭터를 다른 층으로 나누면 안 된다.**
나누는 순간 "캐릭터가 항상 책상 앞" 또는 "항상 책상 뒤"가 되어 입체감이 죽는다.
둘을 같은 정렬 그룹에 넣고 `(x + y)`로 함께 정렬해야
책상 위쪽으로 걸어가면 가려지고 아래로 오면 덮인다.

이게 지금 `DirectionalSpriteAnimator.cs:356~368`에서
**앉을 때만** `sortingOrder`를 바꾸는 임시 처리를 대체한다.

## 3. 목표 구조

```
FamilyCompany.Simulation  (순수 C#, Unity 참조 없음)
└─ OfficeGrid
   ├─ int Width, Height
   ├─ TileKind[,] floor          바닥 종류
   ├─ bool[,] walkable           통행 가능 여부  ← 경로탐색 그래프
   ├─ PlacedFurniture[]          가구 (그리드 좌표 + 방향 + 크기)
   └─ SeatSlot[]                 좌석 (가구에 종속)

FamilyCompany.Presentation.Unity  (View)
└─ Tilemap(바닥) + SpriteRenderer(가구·캐릭터)
   그리드 좌표 → 화면 위치 변환만 담당. 상태를 소유하지 않는다.
```

**격자 데이터는 반드시 `Simulation`에 둔다.** 이유는 프로젝트 규칙 그대로다.

> `AGENTS.md`: MonoBehaviour와 ScriptableObject에 장기 런타임 상태를 저장하지 않는다.
> 시뮬레이션 상태는 순수 C# 객체가 소유한다.
>
> `ARCHITECTURE.md`: 저장 대상은 의미 상태다. Transform은 저장하지 않는다.

지금 배치가 Transform과 아트 픽셀 상수에 흩어져 있어서 **저장할 수가 없다.**
격자로 옮기면 사무실 배치가 `int[,]` 하나로 저장되고, 회차마다 다른 사무실이 성립한다.

## 4. 숫자 — 시작점 제안

지금 스케일이 엉킨 근본 원인은 **PPU가 제각각**이라는 것이다.

| 대상 | 현재 PPU |
| --- | --- |
| 캐릭터 `Frames/` | 180 |
| 캐릭터 `HighMotion/` | **100** |
| 가구 모듈 | 180 |
| 사무실 페인팅 | **100** |

### 요청: PPU를 180으로 통일한다

그 다음 아래를 시작점으로 잡는다. 확정값이 아니라 **첫 시험값**이다.

| 항목 | 값 | 도출 |
| --- | --- | --- |
| 타일 스프라이트 | **320 × 160 px** (2:1 마름모) | — |
| PPU | 180 | 통일 |
| → 셀 크기 | **1.78 × 0.89 world units** | 320/180, 160/180 |
| 카메라 | `orthographicSize = 6.6` (유지) | 보이는 높이 13.2, 폭 23.5 units |
| → 화면에 들어오는 격자 | **약 13 × 13 타일** | 23.5/1.78, 13.2/0.89 |
| 캐릭터 키 | 2.117 units (현행 유지) | 화면 세로의 **16%** ✅ |
| 타일 1개 실측 환산 | 약 1.2 m | 사람 1.7m 기준 |

**13×13이 화면에 딱 들어온다.** 그래서 성장 사다리를 이렇게 잡을 수 있다.

| 단계 | 격자 | 카메라 |
| --- | --- | --- |
| 집 작업공간 | 6 × 6 | 확대 |
| 작은 사무실 | 10 × 10 | 기본 |
| 직원 5명 | 13 × 13 | 기본 |
| 부서 분리 | 20 × 16 | 축소 또는 스크롤 |
| 본사 | 층 개념 도입 | — |

캐릭터 크기는 **지금 계산상 이미 맞다**(16%). 앞 문서에서 잡은 3배 축소는
부모 트랜스폼 스케일 문제이므로, 타일로 옮기면서 부모 체인이 정리되면 같이 해결된다.

## 7. 검증 — 같은 버그가 다시 통과하지 않게

앞 문서에서 지적한 대로 지금 QA는 `localScale == 1.0`만 봐서 **부모 스케일이 곱해지면 통과하면서 화면은 틀린다.**
타일로 옮기면서 검사도 바꿔야 한다.

1. 캐릭터 최종 렌더 높이 ÷ 카메라 높이 = **0.14~0.18**
2. 캐릭터·가구 트랜스폼 체인의 **누적** 스케일이 균등(x == y)
3. 격자 `(0,0)`과 `(W-1,H-1)`의 화면 좌표가 **16:9와 비-16:9 두 종횡비에서** 예상 위치에 있는지
4. `walkable == false`인 칸에 캐릭터가 들어가지 못하는지
5. 캐릭터가 가구보다 위쪽 행에 있으면 정렬 순서가 뒤인지
6. 격자 저장 → 불러오기 후 배치 해시 일치

### 이 판단의 근거

지금 고치는 비용과 나중에 고치는 비용을 비교하면 이렇다.

- **지금 전환**: 사무실이 1개다. 좌표 상수가 수십 개다.
- **1년 뒤 전환**: 사무실이 6단계다. 좌표 상수가 수백 개다. 저장 파일 호환도 깨야 한다.

그리고 지금 안 하면 **가구 배치 편집도, 경로탐색도, 사무실 확장도 전부 못 한다.**

붙일 격자가 없어서 아트 픽셀 좌표에 매달려 있는 상태다.
