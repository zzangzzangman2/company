## 0. 결론 한 줄

> **지금 게임은 "누가 그 일을 하느냐"가 결과를 바꾸지 않는다. 그게 타이쿤이 안 되는 유일한 이유다.**

코덱스가 지금 만들고 있는 것 — 캐릭터가 격자 위를 걸어가 의자에 앉는 것 — 은 필요하다.
그런데 **앉아서 하는 일이 사람마다 같으면** 아무리 잘 움직여도 타이쿤이 아니다.

근거는 코드에 있다.

```csharp
// ContractPortfolio.cs:120
if (family != null && family.Members.Max(member => member.Stats.Development) < offer.RequiredDevelopment)
    return RejectedAcceptance(ContractRejectionReason.DevelopmentInsufficient);
```

능력치가 **"수락 가능한가"의 문턱으로만** 쓰인다.
가족 중 **가장 잘하는 한 명**이 기준을 넘으면 통과하고, 그 뒤로는 **누가 인시를 채우든 결과가 같다.**

`EmployeeStats`에는 능력치가 **10개** 있다.

```
Development · Speed · Stamina · Planning · Art · Sales · Mental · Teamwork · Loyalty · Potential
```

그중 실제로 쓰이는 건 **Development와 Speed 두 개**이고, 그것도 문턱 판정용이다.
**나머지 8개는 저장만 되고 아무 일도 하지 않는다.**

## 1. 벤처 타이쿤(2001)이 실제로 어떤 구조였나

애니미디어, 2001년. 해외명 `Big Biz Tycoon` (Activision, 2002).

### 5개 부서

| 부서 | 역할 |
| --- | --- |
| **연구부** | 기본 분야 외 다른 제품을 만들 능력을 **해금**. 개발·지식 능력치 요구 |
| **개발부** | 프로젝트 개발. **회사 돈을 직접 버는 곳** |
| **관리부** | 봉급·대여비 파악, **자선사업으로 인지도** |
| **유통부** | 제품 판매와 **라이센스 거래**. 급전이 필요할 때 핵심 |
| **홍보부** | **전단지 → 신문 → 유선방송 → 무선방송** 광고 |

### 루프

```
직원 채용 → 부서 배치 → 프로젝트 개발 → 제품 판매 → 수익으로 확장
```

### 그 밖에

- **직원 체력 관리가 가장 중요.** 아이템 제공과 휴식으로 막는다
- **사무실 인테리어**: 책상·의자·컴퓨터는 필수, 장식품은 직원 만족도
- **판매 방식 선택**: 직접 판매 vs 라이센스 판매
- **패배 조건 두 개**: 자본금 부족, 그리고 **상장 후 최대주주 지위 상실 → 경영권 박탈**

### Software Inc.과 비교

같은 구조를 다른 이름으로 부른다.

```
설계 → 프로그래밍 → 디버깅 → 마케팅 → 지원
```

핵심은 이 문장이다. **"작업을 잘못 배치하면 결과가 나쁘거나 적자가 난다."**
팀원 성격 궁합, 교육, 역할 변경, 해고까지 배치가 게임의 전부다.

**두 게임의 공통점은 하나다. 제품이 여러 단계를 거치고, 단계마다 맞는 사람이 다르다.**

## 2. 우리와 대조

| 벤처 타이쿤 | family_company 현황 |
| --- | --- |
| 5개 부서 | **없음.** 업종 4종은 있으나 부서 개념이 없다 |
| 직원 채용 → 부서 배치 | 등급·직군 규칙은 있고 고용 런타임 미연결 |
| 프로젝트 개발 | **있음** (자체 제품 출시) |
| 제품 판매: 직접 vs 라이센스 | **없음** |
| 홍보부: 전단지→신문→방송 | **없음.** 광고·인지도 개념 자체가 없다 |
| 유통부: 급전 조달 | **없음** |
| 직원 체력 + 아이템·휴식 | **있음** (체력·스트레스·회복활동 12종) — 우리가 더 낫다 |
| 사무실 인테리어 (필수 + 만족도) | 타일 이행 중. 만족도 개념 없음 |
| 패배: 자본금 부족 | 부분 |

| 실제 회사 82개·실제 역사 | **있음.** 원작에 없는 우리만의 축 |
| 가족 관계·시간대 제약 | **있음.** 원작에 없는 우리만의 축 |

**우리가 더 나은 것도 있다.** 체력·회복, 실제 역사, 가족 관계는 원작에 없다.
**빠진 것은 전부 "배치와 산출"에 관한 것이다.**

## 3. 추가해야 할 것

### 3-1. 배치가 결과를 바꾸게 만든다 ★최우선

지금: 계약 = 인시 채우면 완료. 누가 채워도 같다.
바꿀 것: 계약을 **단계로 쪼개고**, 단계마다 **다른 능력치**를 본다.

2000년 웹·전산 하청에 맞춘 단계는 이렇다.

| 단계 | 주 능력치 | 이 단계에 약한 사람이 하면 |
| --- | --- | --- |
| 상담·요구 정리 | `Planning`, `Sales` | 요구가 틀어져 뒤에서 재작업이 늘어난다 |
| 제작 | `Development` | 인시가 더 든다 |
| 디자인 | `Art` | 품질이 낮아 수정 요청이 온다 |
| 검수·납품 | `Speed`, `Planning` | 결함이 남아 평판이 덜 오른다 |

**핵심은 실패가 아니라 "비용이 달라지는 것"이다.**
못하는 사람이 하면 못 하는 게 아니라 **인시가 더 들고 품질이 낮다.**
그래야 "그럼 누구를 보낼까"가 매번 고민된다.

이미 `EmployeeStats` 10개가 저장되고 있으므로 **새 데이터는 필요 없다.**
`ContractPortfolio`가 문턱 판정 대신 **기여자별 배율**을 계산하게 바꾸는 것이 전부다.

> **자연스러움과의 연결**: 코덱스가 만드는 착석·이동이 여기서 의미를 얻는다.
> "누나가 저 책상에 앉아 있다"가 "누나가 디자인 단계를 하고 있어서 품질이 오르는 중"이 된다.

### 3-2. 부서 = 가족 4명에는 과하다, 대신 "역할"

원작은 5개 부서에 직원 수십 명이다. **가족 4명에 부서 5개는 성립하지 않는다.**

그래서 초반에는 **역할(Role)** 로 두고, 직원이 늘면 부서로 승격시킨다.

| 인원 | 구조 |
| --- | --- |
| 4명 (지금) | 사람마다 **주 역할 1개**. 아빠=영업, 엄마=관리, 누나=운영, 나=제작 |
| 5~8명 | 역할이 겹치기 시작 → **팀** 개념 등장 |
| 9명 이상 | 원작처럼 **부서**로 승격. 부서장이 배치를 대신한다 |

**지금 할 것은 첫 줄뿐이다.** 4명에게 주 역할을 주고, 역할과 단계가 맞으면 보너스를 준다.
부서 시스템을 지금 만들면 쓸 사람이 없다.

### 3-3. 광고와 인지도 — 2000년 한국에 딱 맞는다 ★값어치 높음

지금 완전히 없고, **없어서 게임이 얇다.** 원작의 홍보부 사다리가 시대와 정확히 맞물린다.

| 수단 | 시기 | 비용 | 효과 |
| --- | --- | --- | --- |
| 전단지·명함 | 2000~ | 아주 낮음 | 동네 반경만. 3차 하청 문의 |
| 지역 생활정보지 | 2000~ | 낮음 | 소규모 업체 문의 |
| 컴퓨터 잡지 광고 | 2000~ | 중간 | 업계 인지도. 2차 하청 자격에 영향 |
| 신문 광고 | 2001~ | 높음 | 원청 협력사 심사에 가점 |
| PC통신·인터넷 배너 | 2000~ | 낮음 | 초고속인터넷 보급률과 연동 |
| 라디오·케이블 | 2003~ | 매우 높음 | 자체 제품이 있을 때만 의미 |

**인지도가 하는 일**: 견적 경쟁 낙찰 확률, 원청 협력사 심사 통과, 자체 제품 초기 판매량.

이게 들어가면 "돈을 벌어서 뭘 하지"에 답이 생긴다. 지금은 현금이 쌓이면 할 게 없다.

### 3-4. 판매 방식 선택 — 직접 vs 라이센스

자체 제품을 냈을 때 원작처럼 두 갈래를 준다.

| | 직접 판매 | 라이센스 판매 |
| --- | --- | --- |
| 수익 | 높음, **느리다** | 낮음, **즉시** |
| 필요한 것 | 유통·광고·재고 | 계약 상대(실제 회사) |
| 위험 | 안 팔리면 재고가 현금을 먹는다 | 상대가 브랜드를 가져간다 |

**라이센스 상대를 History의 실제 회사로 쓸 수 있다.**
"삼성SDS에 라이센스로 넘긴다" vs "우리 이름으로 직접 판다"는 선택은
원작에 없는 우리만의 무게를 가진다.

그리고 이건 **급전 조달 수단**이다. 원작 유통부의 역할이 여기 들어온다.
어음 할인, 대출, 라이센스 매각 — 현금이 마를 때 셋 중 무엇을 고르느냐가 경영이다.

### 3-5. 패배 조건을 확정한다 ★지금 없는 게 이상하다

원작의 패배 조건 두 개가 우리에게 그대로 맞는다.

| 조건 | 우리 상태 |
| --- | --- |
| 자본금 부족 | 부분. 현금이 0이 되면 어떻게 되는지 정의가 없다 |
| **상장 후 최대주주 지위 상실 → 경영권 박탈** | **주식·지분·호가가 다 있는데 연결이 없다** |

두 번째가 특히 아깝다. `SHAREHOLDER_GOVERNANCE_SYSTEM` 계열 설계가 `simul`에 있고
우리에게는 실제 호가창까지 있다. **"상장했더니 경영권을 잃었다"는 엔딩**이
이 게임의 가장 강한 결말이 될 수 있다.

그리고 가족회사라서 한 겹 더 있다. **가족 관계가 붕괴하면?**
`GAMEPLAY_FUN_V1.md`에서 제안한 "14살이 무리하면 부모가 회사를 중단시킨다"가
세 번째 패배 조건이 될 수 있다. 원작에 없는 우리만의 것이다.

## 4. 코덱스와 겹치지 않는 경계선

git log 기준 코덱스는 지금 여기 있다.

```
feat: add smart interaction shadow layer
feat: add authored office locomotion transitions
refactor: add authored subcell furniture collision profiles
```

### 건드리지 않는다

- `Assets/FamilyCompany/Presentation.Unity/OfficeGrid/**`
- `Assets/FamilyCompany/Presentation.Unity/OfficeSeating/**`
- `Assets/FamilyCompany/Presentation.Unity/OfficeRuntime/**`
- `Assets/FamilyCompany/Presentation.Unity/OfficeWorkActions/**`
- `DirectionalSpriteAnimator.cs`, `OfficeWorkerAgent.cs`
- 가구·타일 아트, 인테리어, 만족도

### 안전하다

- `Assets/FamilyCompany/Simulation/Contracts/**` — 단계·배치·능력치 배율
- `Assets/FamilyCompany/Simulation/Company/**` — 광고·인지도·판매 방식
- `Assets/FamilyCompany/Simulation/Family/**` — 역할 배정
- 새 폴더 `Simulation/Reputation/`, `Simulation/Sales/`
- 패배 조건 판정 (순수 규칙)

**전부 순수 C# 계층이다.** 화면은 나중에 붙인다.
`AGENTS.md`가 이미 "시뮬레이션 상태는 순수 C# 객체가 소유한다"고 못박아 뒀으니
경계가 문서상으로도 깔끔하다.

### 접점이 하나 있다 — 미리 합의해야 한다

3-1의 "단계별 배치"가 완성되면, **어느 단계를 하고 있는지 화면에 보여야** 한다.
그건 코덱스의 좌석·상호작용 계층이 표시한다.

그래서 순수 계층이 이런 걸 **읽기 전용으로 노출**해 두면 나중에 배선이 쉽다.

```csharp
// 예시: 좌석에 앉은 사람이 지금 무슨 단계를 하는지
ContractStagePresentation { memberId, contractId, stage, progress01, qualityHint }
```

**지금 만들 것은 이 데이터뿐이다. 표시는 코덱스가 자기 계층에서 한다.**

## 6. 성공 판정

구현 후 이 질문에 "예"가 나오는지로 본다.

1. 같은 계약을 **다른 사람에게 맡기면 결과가 다른가?** (인시, 품질, 평판)
2. "이 일은 누나가 해야 한다"는 생각이 드는가?
3. 현금이 쌓였을 때 **쓸 곳이 있는가?**
4. 질 수 있는가? 어떻게 지는지 아는가?
5. 상장이 이득만이 아니라 **위험**으로도 느껴지는가?

지금 상태로는 1·2·3·4·5가 전부 "아니오"다.
1번과 2번은 순위 1~2로, 3번은 4번으로, 4·5번은 순위 3으로 해결된다.
