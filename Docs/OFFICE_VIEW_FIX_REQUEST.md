## 1. 캐릭터가 가구에 비해 약 3배 작다 ★최우선

### 증상

실행 화면에서 인물 두 명이 개미만 하다. 누가 누구인지, 무엇을 하는지 알아볼 수 없다.
책상 하나가 인물 다섯 명을 합친 것보다 넓다. 사무실이 아니라 인형의 집처럼 보인다.

### 측정 (소스 실측값)

| 항목 | 값 | 근거 |
| --- | --- | --- |
| 캐릭터 프레임 | 512×512 px | `Assets/Art/Characters/Player/Pixel/Frames/player_east_a.png` |
| 프레임 안 피사체 bbox | 244×381 px (세로 74.4%) | 알파 경계 측정 |
| 프레임 PPU | 180 | `Frames/*.png.meta`, `HighMotionCharacterArtBuilder.PixelPixelsPerUnit` |
| → 피사체 월드 높이 | **2.117 units** | 381 ÷ 180 |
| 사무실 카메라 | `officeOrthographicSize = 6.6` | `IsometricCameraFollow.cs:19` |
| → 화면에 보이는 월드 높이 | **13.2 units** | 6.6 × 2 |
| → 캐릭터가 차지해야 할 화면 비율 | **16.0%** | 2.117 ÷ 13.2 |
| → 1080p 기준 예상 키 | **약 173 px** | — |
| **실제 화면에서 관측된 키** | **약 50 px (약 5.8%)** | 실행 캡처 |

**계산상 나와야 할 크기의 약 1/3로 렌더된다.** 어딘가에서 캐릭터가 3배쯤 줄고 있다.

### 확인해 볼 곳

- `OfficeVisualV2Presenter.cs:156` — `renderer.transform.localScale = Vector3.one * characterVisualScale`
  `DefaultCharacterScale = 1f`이고 `OfficeVisualV2IntegrationQa`가 1.0을 단언한다. 그럼 여기는 아니다.
- **캐릭터 루트의 부모 체인에 1보다 작은 스케일이 있는지.**
  배경은 `AlignLayer`가 평면을 회전·스케일해서 붙인다(`OfficeVisualV2Presenter.cs:438~454`).
  캐릭터가 그 평면의 자식이라면 평면 스케일을 그대로 상속한다. 가장 유력한 후보다.
- `HighMotion` 폴더 시트는 PPU가 **100**이고 `Frames`는 **180**이다. 서로 다른 PPU의 시트가 섞여 쓰이는지.
- 실제로 씬에서 쓰이는 스프라이트가 `Frames/`(512px, PPU 180)가 맞는지, 아니면 다른 경로인지.

### 요청

1. 캐릭터 최종 렌더 높이를 **화면 세로의 14~18%** (1080p에서 150~190 px)로 맞춘다.
2. 그 값을 상수 하나로 두고 QA가 **실제 렌더 결과**를 검사하게 한다.
   지금 `OfficeVisualV2IntegrationQa`는 `localScale`이 1.0인지만 보는데,
   부모 스케일이 곱해지면 그 검사는 통과하면서 화면은 틀린다.
   `renderer.bounds.size.y`를 카메라 `orthographicSize`와 비교하는 검사로 바꿔야 한다.

### 수용 기준

- GPU 캡처에서 **캐릭터 키 ÷ 화면 높이가 0.14~0.18** 범위에 들어온다.
- 누나·아빠·엄마·플레이어를 서로 구분할 수 있다.
- 책상 앞에 섰을 때 사람이 책상보다 크다.

## 2. 캐릭터가 찌그러져 보인다

### 증상

인물이 뭉개지고 세로로 눌린 것처럼 보인다.

### 원인 후보 둘

**(a) 과도한 축소 리샘플링**
512×512 원본을 50 px로 줄이면 약 1/10 축소다. Point 필터로 1/10을 줄이면 픽셀이 규칙적으로 버려져서
선이 끊기고 뭉개진다. **1번을 고치면 상당 부분 같이 해결된다.**

**(b) 비균등 스케일**
`AlignLayer`가 배경에 x·y를 **따로 계산한** `localScale`을 넣는다.

```csharp
renderer.transform.localScale = new Vector3(
    targetWidth  / size.x,
    targetHeight / size.y,
    1f);
```

카메라 종횡비가 `TargetAspect`(1666/937 = 16:9)와 다르면 x와 y 배율이 달라져 **배경이 늘어난다.**
캐릭터가 이 평면의 자식이면 캐릭터도 같이 늘어난다.

### 요청

- 캐릭터에는 **절대 비균등 스케일이 적용되지 않도록** 보장한다.
- 배경도 비균등 스케일 대신 **균등 스케일 + 레터박스**로 바꾸는 걸 검토한다.
  창 크기 조절을 허용하는 이상(`FRONTEND_V0_4.md`) 16:9가 아닌 종횡비가 실제로 들어온다.
- 캡처를 **16:9가 아닌 창**에서도 한 장 떠서 비교한다. 지금 QA는 16:9만 본다.

## 3. 16:9 고정 가정이 좌표를 어긋나게 한다

### 증상

사용자 보고: "책상을 막 위로 옮기고 크기도 안 맞는다."

### 측정

`OfficeVisualV2Presenter.cs:434`

```csharp
var visibleWidth = visibleHeight * TargetAspect;   // TargetAspect = 1666/937 = 1.778 고정
```

주석에 배치모드에서 4:3으로 잘못 잡히는 걸 막으려 고정했다고 적혀 있다.
그런데 실제 플레이는 **창 크기 조절이 허용된 PC 빌드**다.
카메라의 실제 `aspect`가 1.778이 아니면 배경이 채워지는 폭과 카메라가 보는 폭이 달라진다.

한편 좌표 변환은 실제 종횡비를 쓴다.

```csharp
artPixel = OfficeVisualV2Calibration.ViewportToArtPixel(viewport, viewCamera.aspect);   // :190
```

**배경 배치는 고정 종횡비, 좌표 변환은 실제 종횡비.** 둘이 어긋나면
아트 픽셀로 지정한 책상·의자·경유점이 화면상 실제 그림과 다른 자리에 찍힌다.

### 요청

- 배치와 좌표 변환이 **같은 종횡비 기준**을 쓰게 통일한다.
- 배치모드 오탐 문제는 종횡비를 상수로 박는 대신 **캡처 시 RenderTexture 종횡비를 명시**하는 쪽으로 옮긴다.
- 16:9가 아닌 창에서는 레터박스를 넣고, 레터박스 영역을 좌표 변환에서 제외한다.

### 수용 기준

- 1920×1080, 1600×900, **그리고 임의 크기로 늘린 창** 세 가지에서
  책상 4개의 화면상 위치가 배경 그림의 책상과 정확히 겹친다.

## 6. 아트 스타일이 두 갈래다

배경은 **손으로 그린 부드러운 등각 일러스트**(1920×1080 페인팅)이고,
캐릭터는 **도트**다. 두 화풍이 한 화면에 있으면 캐릭터가 배경에 얹힌 스티커처럼 보인다.

크기를 키우면 이 대비가 **더 강해진다.** 1번을 하기 전에 방향을 정하는 게 낫다.

### 선택지

| 방향 | 내용 | 비용 |
| --- | --- | --- |
| **A. 캐릭터를 배경 화풍에 맞춘다** | 도트 대신 같은 소프트 렌더로 다시 그린다 | 큼. 12인분 재작업 |
| **B. 배경을 도트로 내린다** | 배경에 픽셀화 후처리를 걸어 해상도를 낮춘다 | 중간. `PixelatedCameraEffect`가 이미 있다 |
| **C. 지금대로 두고 크기만 맞춘다** | 대비를 감수한다 | 없음 |

**권장은 B다.** `PixelatedCameraEffect`가 이미 프로젝트에 있고,
2000년대 한국 사무실이라는 소재에 도트가 더 맞는다. 무엇보다 **에셋 재작업이 없다.**
다만 배경 페인팅의 디테일이 뭉개지므로 한 장 시험 렌더를 떠서 사용자 판단을 받는 게 좋다.

## 8. 검증 방법

지금 QA가 이 버그들을 통과시킨 이유가 검사 방식에 있다.

- `OfficeVisualV2IntegrationQa`는 `localScale == 1.0`만 본다.
  **부모 스케일이 곱해지면 통과하면서 화면은 틀린다.**
- 캡처 QA가 16:9 하나만 본다. 창 크기 조절을 허용하는데 다른 종횡비를 안 본다.

### 요청하는 새 검사

1. `renderer.bounds.size.y / (camera.orthographicSize * 2)`가 **0.14~0.18**인지
2. 캐릭터 트랜스폼 체인 전체의 누적 스케일이 **균등**한지 (x == y)
3. 책상 4곳의 **아트 픽셀 좌표 ↔ 화면 픽셀 좌표**가 일치하는지, **16:9와 비-16:9 두 종횡비에서**
4. 캐릭터가 책상 위쪽에 있을 때 `sortingOrder`가 책상보다 뒤인지
